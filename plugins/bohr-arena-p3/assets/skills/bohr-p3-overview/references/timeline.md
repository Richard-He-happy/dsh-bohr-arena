## 二、关键节点与判据

### 节点 1：Day1 首轮出分 —— 区分三类低分

- 现象：多数题 55–70；个别题 0；个别题报 `evaluation_error`。
- 判据：同一题 2 次以上 0 分、且报错为评测链路失败 → 记为"链路 0 分"，**不要继续重 roll**。
- 动作：链路 0 分 → 极简重做或换元数据重试 1 次；质量低分（55–65）→ 极简重做/patch。

### 节点 2：极简重设计验证（Day2）

- 触发：有 ≥3 道 0 分题或大量 <60 分题。
- 做法：从零写极简包（SKILL.md + ≤2 脚本 + ≤2 references；`init/show/check/build`；`build` 无工作稿也产完整最小交付）。
- 验收：本地 eval 等价冒烟通过后再提交；单题先验证 1–2 个，再批量推广。
- 实测：三道 0 分题分别 0→59、0→71.67、0→69.67，随后推广到全部低分题。

### 节点 3：patch 有效性的分界（Day3）

- patch = 在 best 包上**增补可核验资产**（页级金标准、逐页 diff、版本记录、运行日志、导出检查、自检），不改原有调用与产物。
- 有效题型：幻灯片、阅读、写作（+2~+21）。
- 无效题型：图形绘制类（多数掉分）。
- 判据：题面 rubric 明确有"结果可核验性/完整性/生态贡献"类得分点，且现有包缺对应资产。

### 节点 4：评测标准漂移（Day3 上午）

- 现象：同一批包在 11:00 之后创建的提交普遍多拿 +15~20 分，多题出现同一分档（83）。
- 判断：平台评测器/评分模型重新校准（属于推断，无法从外部确认）。
- 动作：**全量重提当前最佳包**（复用已有 trace、升级 CLI），不要改包。
- 实测效果：多题从 60–68 直接落到新档位，是本期单次收益最大的动作之一。

### 节点 5：队列拥堵与"弹药"管理（Day4 起）

- 现象：队列约 0.3–0.5 位/分钟（≈790/天），出分 12–28 小时。
- 推论：在队 attempt 数 = 未来 1–1.5 天的期望出分。
- 动作：把"每题 pending 2–3 个"当作预算；autoroll 式自动补投比人工冲动提交稳定。

### 节点 6：最后 48 小时

- 只重提已验证最佳包；不再改包结构；不引入新方案。
- 截止前 2–3 小时停止提交：迟到提交可能来不及评测。
- 保留"最佳包快照 + 可回滚"，任何新动作都不能破坏已有最佳版本。

## 三、每日 2 小时循环（模板）

1. **扫描**：拉每题最佳分与 pending 数（或读平台单题榜）。
2. **决策**：按策略决策树给每题选动作（重 roll / patch / 极简重做 / 不动）。
3. **执行**：单轮 4–6 条重 roll + 1–2 个构建任务（云端并发 2–3，串行打包）。
4. **记录**：更新"每题当前最佳版本"，写清动作、时间、下次检查点。
5. **风控**：改包前先归档；云端失败不覆盖已有包；提交失败先确认上传通道是否可用。
