# 玻尔产品赛第三期（学术效率）全景

## 1. 用途与何时使用

把「33 道主赛题 / 4 条赛道 / 隐藏案例评测 / 按赛道总分排名」这类多题并行 Agent Skill 竞赛的打法做成一页可执行的全局视图：

- 初次进入同类比赛：先确定**总策略与投递节奏**，再逐题设计 Skill。
- 中途复盘：判断当前处于哪个阶段、下一步该重 roll 还是重设计。
- 需要回答"这题用什么手段提分"时，直接查第 5 节决策树。

不适用：单题单次交付（那属于题级打法，见 `bohr-p3-task-playbooks`）；只看单包工程质量（见 `bohr-p3-skill-blueprint`）。

## 2. 赛制与计分（规则要点）

| 项 | 事实 | 对策略的含义 |
|---|---|---|
| 题量 | 33 道主赛题：reading 10 / writing 14 / graphics 5 / slides 4；另有 1 道附加题 | 阅读+写作为主战场（24/33），图形与幻灯片题少但单题权重大（每道最多约占总分 1/5 的赛道） |
| 赛道总分 | 该赛道各主赛题得分之和（+ 附加题加分）；**同分先达到者靠前** | 空题=0 分；补齐一题的平均收益=该题得分，所以"先全量、再提分" |
| 单题榜 | 每题按每人最佳一次提交计 | 同题可多版本覆盖、取最好，不存在"提交越多越亏" |
| 评测方式 | Skill 包被装进官方 Harness，在 **3 个固定隐藏案例**上真实回放运行，再按题面 rubric 打分 | 评审看**运行产物**，不看 SKILL.md 自述；写的和跑的要一致 |
| rubric | 实际效果 40（完成度 15 / 正确性 15 / 完整性 5 / 可核验 5）+ 使用增益 25 + 创新 15 + 可靠 10 + 生态 10 | 60 分在前两项；"完整 + 可核验 + 真实推导"是主矛盾 |
| 提交 | 命令行提交，需带输出目录、真实 Agent 原生会话 trace、模型与 harness 元数据 | trace 不可伪造；提交前先 `trace validate` 通过 |
| 反馈周期 | 首日排队 600+，出分 2–4 小时；拥堵期队列约 0.3–0.5 位/分钟（≈790/天），出分 12–28 小时 | 提分动作必须**提前排进队列**；不能"等出分再改"式循环 |

## 3. 成绩演进（阶段划分与相对变化）

| 阶段 | 动作 | 相对结果 |
|---|---|---|
| Day1 全量首版 | 云端逐题建包（单题 16–35 分钟），33/33 全部提交 | 多数题落在 55–70 区间，少数题 0 分；赛道内"人人有分" |
| Day1 夜–Day2 | 零分救援：极简 agent-first 重设计（`init/show/check/build`） | 3 道 0 分题分别 0→59、0→71.67、0→69.67；低分题普遍 +5~+72 |
| Day2 | 融合重写（旧完整版+极简版融合） | 10 个融合包 **0 个**超过原最佳，正式放弃 |
| Day3 上午 | 按 rubric 做 patch：增补"页级金标准/逐页 diff/版本记录/导出检查"等可核验资产 | 幻灯片两题 +19~21（63.67→83、62.33→83）；图形题掉分 |
| Day3 中午 | 发现评测标准整体抬高：11:00 后创建的提交，多题同一批包拿到 83（较此前 +15~20） | 动作=**全量 33 题重提当前最佳包**，吃新标准 |
| Day4 起 | 队列积压（0.3–0.5 位/分钟），反馈 12–28 小时 | 改为"待评分弹药"管理：每题保持 2–3 个 pending |
| 收官 | 只重提已验证最佳包；冻结后不再改包 | 避免"新包未出分 + 旧包被替换"的双输 |

**可操作读法**：单题分数上限由"产物完整、可核验、真正推导"决定；短期分数主要靠"多版本覆盖 + 取最好"逼近上限，而不是靠把 SKILL.md 写得更长。

## 4. 核心实证结论（附依据类型）

| # | 结论 | 依据 | 用法 |
|---|---|---|---|
| 1 | **0 分基本等于评测链路失败（evaluation_error），不是质量 0**；失败提交约占总提交 18% | 实测：同一包不同提交出现 0 与 83；题面/台账里 0 分题多为 evaluation_error | 不要把 0 分当低分继续重 roll；先判因 |
| 2 | 同包重 roll 有稳定正收益，方差 8–15 分（第三期实测 8–13），常见 +2~+8 | 实测 | 60 分以上题的主力提分手段 |
| 3 | 同一包在不同评测 run 中分数可差到 0/60/83 | 实测 | 高分题也要保留多个 attempt；不要用单次结果否定设计 |
| 4 | 极简 agent-first（Agent 主答 + 脚本辅助 + 兜底必成）是最高 ROI 的重设计 | 实测：0→59~71.67，之后推广到全部低分题 | 0 分/55 分以下的默认做法 |
| 5 | "融合重写"（两个包合并自由改写）成功率约 1/10，且失败代价是 0 或低分 | 实测：10 个融合包 0 提升 | 除非无 v1 可用，不做融合 |
| 6 | patch（在 best 包上**增补**可核验资产，不改调用）在内容/结构型题有效 | 实测：幻灯片 +19~21；阅读/写作题 +2~+7 | slides/reading/writing 的 55–65 分题首选 |
| 7 | patch 在图形绘制类题上多数掉分，仅个别有效 | 实测：4 题中 3 题低于原最佳，1 题 +1.33 | graphics 不用 patch，用"质量强化 v3"+重 roll |
| 8 | CLI 版本影响很大：升级 0.1.49→0.1.50 时同包 +13；过期版本会污染 stdout | 实测 | 每天开工先查版本，过期立即升级 |
| 9 | 平台评测标准会漂移（某天上午约 11:00 后整体抬高 +15~20） | 实测 + 推断（无法从外部确认口径） | 对策：发现集体抬升就"全量重提最佳包"，不重做包 |
| 10 | 主脚本 >30KB 或文件数 >8 时评测失败概率显著升高 | 实测反馈 + 推断 | 包体红线写进构建约束 |
| 11 | 队列吞吐约 790/天：在队 attempt 数 = 未来 1~1.5 天的期望出分 | 实测速率测算 | 用 pending 数量管理提分节奏，而不是"想到才提交" |

## 5. 策略决策树（按"当前单题最好分 + 题型"选手段）

```
单题当前最好分
├─ 0 分（且同一包多次 0 / 出现 evaluation_error）
│   ├─ 包极小（≤4 文件/≤30KB）仍 0 → 换 model/harness 元数据再试 1 次；仍 0 则降频，保 1 个候选
│   └─ 包较大或结构复杂 → 极简 agent-first 重做（最高优先级）；不要继续重 roll 旧包
├─ 45–65 分
│   ├─ 模板/格式/幻灯片类 → patch 增补可核验资产（页级金标准、逐页 diff、版本记录、导出检查）
│   ├─ 阅读/写作内容型 → patch 或极简重做，两者都先做本地 eval 等价冒烟
│   └─ 图形绘制类 → "质量强化 v3"：拉高元素/关系数量与真实导出，再重 roll
├─ 65–78 分 → 同包重 roll 2–4 条（主力）；不看题型
└─ 78 分以上 → 低频重 roll 冲上尾；冻结包结构，只保分
```

题型与手段的匹配（实测结论）：

| 题型 | 首选 | 次选 | 明确不要 |
|---|---|---|---|
| 阅读问答/提取/核验/清洗 | 极简重做（Agent 逐条读原文） | patch 补金标准/diff | 融合重写；脚本抽取式作答 |
| 写作长文档/章节/翻译/基金/开题 | 极简重做；v1 稳定后重 roll | patch 补 workorder 回执 | 融合重写（结构易被带偏） |
| 图形（示意图/机制图/装置图/图表/图形摘要） | 质量强化 v3 + 重 roll | 极简重做 | patch（多数掉分） |
| 幻灯片（生成/编辑/组织/模板适配） | patch（金标准+逐页 diff+导出检查） | v1 + 重 roll | 融合重写；给已有导出路径的包硬塞劣质 PDF 兜底 |

## 6. 投递节奏与资源分配

1. **Day1–Day2：33/33 全量首版**。优先级 reading/writing（题多、赛道总分权重大），graphics/slides 次之；宁可 60 分全覆盖，也不要 1 题 83、其余空题。
2. **稳定期（每天 2 小时循环）**：扫榜 → 更新每题最佳分 → 提交 4–6 条重 roll + 1–2 个 patch/重做 → 记录。单轮不要超过 6 条，避免队列过长。
3. **队列拥堵期**：只"补位"不改结构；以 pending 数量（每题 2–3 个）为预算，不按心情提交。
4. **最后 48 小时**：不改包结构；只提交已验证最佳包；截止前 2–3 小时停止提交（迟到提交可能来不及出分）。
5. **平台故障后**（上传通道故障、502 等）：先单条探测恢复，再集中批量重提——故障恢复后的第一波队列最划算。

## 7. 顶层失败模式与对策

| 失败模式 | 典型现象 | 对策 |
|---|---|---|
| 空题丢分 | 只做了少数题的高分，赛道总分落后 | 先 33/33；再逐题提分 |
| 把 0 分当低分 | 对 evaluation_error 反复重 roll，浪费队列 | 先按第 4 节 #1 判因；0 分题做重设计或多版本覆盖 |
| 加功能膨胀 | 文件数 20+ / 主脚本 50–90KB，掉分最狠 | 极简：SKILL.md + ≤2 脚本 + ≤3 references |
| 模板/格式题自由重写 | 幻灯片、模板适配题重写后掉分 | patch 或保留 v1；只重 roll |
| 云端超时截断 | 产物有脚本没 SKILL.md，包不可用 | 任务书第一步先写 SKILL.md 骨架；超时改 55 分钟；同会话续跑 |
| 把 pending 误判为失败 | 反复重提同一题，队列翻倍 | 区分 queued/evaluating/scored/failed；按出分窗口排动作 |
| 单次结果否定设计 | 一次低分就推翻重做 | 方差极大：同包 2–3 次再判断 |

## 8. 自检清单（开赛/复盘时逐项过）

- [ ] 33 题清单（key/赛道/题名/契约形态）已建表，与官方题号对齐。
- [ ] 33/33 均有首版提交，无空题。
- [ ] 每题保留"当前最佳包"快照，且可一键回滚（改包前先归档）。
- [ ] CLI 已确认最新版本，提交脚本能处理 stderr 告警污染 stdout。
- [ ] 每题 pending 数量可见，重 roll 队列有上限（单轮 4–6 条）。
- [ ] 已知 0 分题已分类（evaluation_error / 设计缺陷）并各有对应动作。
- [ ] 已记录"提分手段 → 题型"的匹配表，避免对图形题用 patch、对模板题用融合。
