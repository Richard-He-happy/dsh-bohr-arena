# 故障、判断与恢复顺序

> 原则：先判断"是谁的问题"（包 / 本地环境 / 平台侧），再决定"重试 / 修包 / 等恢复"。所有失败都要留日志，且**不得覆盖当前最佳包**。

## 一、快速分诊表

| 现象 | 最可能原因 | 第一步 | 恢复动作 |
|---|---|---|---|
| 云端产物只有 scripts、没有 SKILL.md | 云端超时截断（默认超时太短 / 首步没写骨架） | 查云端会话状态与产物清单 | 同会话发"收尾指令"续跑 → 重新打包；下一轮任务书要求第一步先写 SKILL.md |
| 云端返回 HTML 页面而非 API JSON（HTTP 502） | 平台侧网关故障 | 看平台健康接口是否正常 | 降并发到 2–3、自动重试 ≤3 次（间隔 90 秒）；从上一版包恢复，不覆盖 |
| 打包下载了整个工作区（含 demo/upload） | 前缀识别失败（云端没写 SKILL.md） | 查产物清单里有没有 submission/SKILL.md | 按白名单清包；若确实没有 SKILL.md → 判本轮失败，重跑 |
| 多任务并行时报 "state.lock: The file exists" | 本地 CLI 状态锁冲突 | 查是否有并行云端任务 | 改为串行批次；同一时刻只跑一个云端动作 |
| 提交报网络超时（无网络活动 600 秒） | 平台上传通道故障 | 用单条小包探测 | 暂停批量提交；每 20–30 分钟单条探测；恢复后集中重提（先补最缺分的题） |
| 提交命令输出被告警污染、JSON 解析失败 | CLI 版本过期（版本告警写到 stderr，混入输出） | 查 CLI 版本 | 升级到最新版本；解析时截取第一个 JSON 片段兜底 |
| 本地校验进程长时间不退出 | 子进程挂死（无超时保护） | 看进程与输出文件 | 用超时 + 进程树强杀；恢复后重跑（不要重复启动第二个实例） |
| 同一题出现多个云端会话、产物互相覆盖 | 批量脚本重复启动 | 查会话记录与批次日志 | 每题只保留一个 launcher；先查记录再启动 |
| 包在评测中 0 分 / evaluation_error | 评测链路失败或包结构问题 | 看是否同包多次 0、是否报 evaluation_error | 见下方"评测侧故障" |
| PowerShell 脚本被拦截 | 执行策略 | 进程级设置 Bypass | 再调用；注意不要给内置自动变量赋值（如 `$args`） |

## 二、云端构建故障的恢复顺序

1. **停**：停止继续启动新会话（避免并发 502 与锁冲突扩大）。
2. **看**：读本轮会话的日志、产物清单、回答文本；确认失败发生在"建会话 / 上传 / 生成 / 打包"哪一步。
3. **救**：如果是超时截断 → 同会话续跑收尾；如果是 502 → 等待后重试；如果是上传失败 → 重传缺失文件。
4. **验**：重新打包后检查是否含 SKILL.md、文件数/体积、是否混入 `__pycache__`/demo。
5. **换**：仍失败则改本地直接写最小包（本地也能产原生 trace），或降低目标（先交 partial 版本）。

## 三、打包与版本安全

- **先暂存再替换**：下载到暂存目录 → 校验 `SKILL.md` 存在 → 归档旧包（时间戳）→ 替换。任何一步失败都不动当前包。
- **归档命名**：`当前包` 与 `历史快照` 分开；每次提交记录对应的包版本，出分后能回答"这个分是哪个包拿的"。
- **回滚**：patch/重设计失败时，把历史快照换回当前包再提交（实测多次用到，尤其"融合重写"与"给正常包硬加劣质 PDF 兜底"两类失败）。
- **清理**：提交前按白名单清包；`__pycache__`、`.pyc`、临时输出、示例二进制一律不带。

## 四、评测侧故障（0 分 / evaluation_error）

| 观察 | 解释 | 动作 |
|---|---|---|
| 同包多次 0 分，且报 evaluation_error | 评测链路失败（不是质量 0） | 换元数据（模型/harness）再试 1 次；仍 0 → 走"极限稳健版"重做一个极小的包 |
| 同包一次 0、一次高分 | 评测高方差 | 继续用同一包重提，取最好；不要因为一次 0 分改设计 |
| 包体偏大（主脚本 >30KB / 文件 >8）后开始频繁失败 | 复杂包更易在评测环境跑挂 | 拆功能、砍依赖、回到极简；先保证"能跑完" |
| 小包也连续 0 分（5 次以上） | 该题对当前包有系统性失败 | 保 1 个最小候选，降频；把精力放到其他题；有明确原因再修 |
| 平台标准突然整体抬高（同一批包集体多拿 15–20） | 评测口径漂移 | 全量重提当前最佳包，不改包 |

## 五、自动化守护的故障处理

- **扫描脚本报错**：先看是接口变化还是网络问题；不因单次报错重启整条流水线。
- **autoroll 重复提交同题**：检查"无 pending"判据是否依赖了过期状态；加"最近 N 小时内已提交则跳过"。
- **autoroll 超出队列预算**：把每轮上限从 5–6 条降到 3–4 条，优先"分数最低且题型适配"的题。
- **定时任务丢失**：守护进程每轮检查关键任务是否存在，缺失且仍有待办时重建（带剩余清单）。
- **所有自动动作的共同底线**：只重提已验证的包、只记录不改包、失败留日志、可随时手动停机。

## 六、提交失败后的重试策略

1. **分类**：包问题（缺 SKILL.md、缺 trace、包体超限）→ 修；通道问题（网络超时、502、鉴权 401）→ 等。
2. **探测**：用一条最小包提交做探针；成功才恢复批量。
3. **批量**：恢复后按"分数缺口从大到小"排序重提，不要一次全量压上去（队列会堵）。
4. **记录**：每次失败/成功的提交都写进题目提交清单（时间、包版本、结果、原因），用于后续方差判断。

## 七、复盘检查（每天一次）

- [ ] 当天所有失败是否都已分类（包 / 本地 / 平台）？
- [ ] 是否有题因"通道故障"而漏掉提交窗口？需不需要补投？
- [ ] 当前最佳包是否有快照、是否可回滚？
- [ ] 自动化的失败率是否上升（>10% 就要降频并查原因）？
- [ ] 队列待评分数量是否在预算内？
