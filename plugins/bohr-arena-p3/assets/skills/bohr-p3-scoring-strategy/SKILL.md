# 评分与提分实证

## 1. 用途与何时使用

回答"这一分该怎么提"：手上有一道题的当前最佳分，要不要重 roll、要不要改包、改哪种包、现在提交还是等等。

- 手上是平台分数与提交记录 → 按第 2–8 节判断该题处在什么状态。
- 要排未来 48 小时的行动 → 直接看第 9 节与 `references/decisions.md`。
- 需要数据依据 → `references/evidence-log.md`（匿名化数据点）。

不适用：包本身怎么写（`bohr-p3-skill-blueprint`）；逐题打法（`bohr-p3-task-playbooks`）。

## 2. 评分模型（先理解分数是怎么来的）

- Skill 包被装进官方 Harness，在 **3 个固定隐藏案例**上分别运行，按题面 rubric 打分；`harbor_replay_executed` 表示真实回放成功。
- rubric 五维：实际效果 40（完成度 15 / 正确性 15 / 完整性 5 / 可核验 5）+ 使用增益 25 + 创新 15 + 可靠 10 + 生态 10。
- **评审看运行产物与真实推导**：SKILL.md 写得多不加分；"加功能、堆文件"在实测中掉分最狠。
- 分数是"包质量 × 评测链路成功率 × 评测方差"三者的产物——这决定了提分手段不是单一的。

## 3. 0 分的真实含义：基本等于 evaluation_error

| 观察 | 结论 |
|---|---|
| 同包多次 0 分，且报 `evaluation_error` | 评测链路失败，**不是质量 0**；失败提交约占总提交 18% |
| 同一包一次 0、一次 83 | 评测高方差；0 分不可用来否定设计 |
| 0 分题在小包（≤4 文件/≤30KB）下仍连续 0 | 该题对当前包有系统性失败（实测出现过连续 5 次）→ 走极限稳健版或降频 |

操作：遇到 0 分先问三句——「是 evaluation_error 吗」「同包是否曾有高分」「包是否偏大」。三问不清就不要用"继续重 roll"当解法。

## 4. 评测方差：为什么"多提交取最好"是主策略

- 同题不同 attempt 的分差常见 **8–15 分**（第三期实测 8–13）。
- 极端情况同一个包可差到 **0 / 60 / 83**。
- 结论：单次结果不足以判断设计好坏；**同一最佳包反复提交、取最高分**是风险最低的提分手段。

**重 roll 的操作规范**：

1. 只重提"当前最佳包"（不要顺手改包）；
2. 每次换新的真实 Agent 原生会话 trace；
3. CLI 保持最新版本；
4. 每题单轮 2–4 条，同题不同 attempt 时间错开；
5. 记录每次提交与结果，算出该题方差再决定追加条数。

实测收益：稳定 +2~+8 分；个别题能到 +8；高分题（75+）也有上尾空间。

## 5. patch 增补：按 rubric 补"可核验资产"

**定义**：在 best 包上**最小增补**（不改调用方式、不重写结构），补上 rubric 里"结果可核验性/完整性/生态贡献"对应的资产：

- `golden_standard.json`（核心交付的金标准，逐项带 locator+quote）
- `diff_report.md`（实际产物 vs 金标准逐项对照）
- `version_history.md`（版本与回退）
- `run.log`（运行日志）
- `self_check.json`（契约完整性/证据覆盖率/一致性/兜底测试结果）
- `result.json` 增加对应字段（原契约字段一个不少）

**有效边界（实测）**：

| 题型 | patch 效果 | 说明 |
|---|---|---|
| 幻灯片（生成/编辑/模板适配） | **+19~21**（63.67→83、62.33→83） | 页级金标准/逐页 diff/版本记录/导出检查正是 rubric 的"完整与可核验"得分点 |
| 阅读、写作 | +2~+7（个别 +6.67） | 有效但幅度小 |
| 图形绘制 | 多数掉分（4 题中 3 题低于原最佳，1 题 +1.33） | 图形题的主要矛盾是图本身质量，不是资产数量 |

**反例**：给"本来有可用渲染路径"的幻灯片包强加劣质 PDF 兜底 → 57.67 vs 原 83。patch 只补"确实缺的件"。

## 6. 融合重写：正式否定的路线

- 做法：把"极简版"与"旧完整版"两个包一起给云端 Agent，要求融合优点重写。
- 战绩：10 个融合包 **0 个**超过原最佳；多数掉到 50–60，个别 0 或 evaluation_error。
- 根因：包更大更复杂 → 评测 Agent 更难按主路径走；结构被自由重写带偏；脚本更多更易跑挂。
- 结论：**放弃融合重写**。只在"没有可用 v1、且题目低于 55 分"时才考虑重写，且优先"极简重做"而不是"两包融合"。
- 附带教训：融合包暴露的评测失败与包体正相关（主脚本 >30KB 或文件 >8 时失败概率显著升高）。

## 7. 评测标准漂移：可遇不可求的一波

- 现象：某天上午（约 11:00）之后创建的提交，多道题、不同题型都拿到同一分档（83），较此前同质量包 +15~20。
- 判断：平台评测器/评分模型重新校准（推断，无法从外部确认）。
- 动作：**立即全量重提当前最佳包**（复用 trace、升级 CLI、不改包）；一次动作让多赛道同时抬升，是本期单次收益最大的操作。
- 防御：保持"每题最佳包可随时重提"的状态（包在、trace 有效、CLI 最新），才能吃到这种窗口。

## 8. 提分手段排序（按 ROI 与风险）

| 顺序 | 手段 | 适用 | 收益量级 | 风险 |
|---|---|---|---|---|
| 1 | 同包重 roll | 55 分以上全部题 | +2~+8/次，方差收益 | 低（只耗队列） |
| 2 | 全量重提（标准漂移时） | 全部题 | +15~20/题 | 极低（不改包） |
| 3 | 极简 agent-first 重做 | 0 分与 <60 分题 | 0→59~71.67 | 中（新包需冒烟） |
| 4 | patch 增补 | 幻灯片/阅读/写作的 55–65 分题 | +2~+21 | 中低（可回滚） |
| 5 | 质量强化 v3（图形） | 图形题 | 单题 +2~+10（目标） | 中（要真实导出与断言） |
| 6 | 换 model/harness 元数据重试 | 0 分且小包也 0 的题 | 不确定 | 低 |
| 7 | 融合重写 | —— | 实测 0 提升 | 高，**不用** |

## 9. 门槛与赛程决策

- **门槛会涨，而且涨得快**：实测某赛道门槛在 1.5 小时内上涨 33 分；中游队伍密集，自己涨分时门槛常同步上涨（推断：同分段选手数量大）。
- **安全垫原则**：不要满足于踩线；目标留 **15–25 分**缓冲。6 天赛程里，最后 48 小时的增量往往被门槛上涨吃掉。
- **何时停止提分**：当"继续提交的边际收益 < 队列来不及出分的风险"时停；截止前 2–3 小时停止提交。
- **何时集中冲某一赛道**：只在该赛道"单题平均分 × 可提分题数"明显大于其他赛道时；否则优先补"分最低且上限高"的题。
- **队列即弹药**：队列约 790/天；每题保持 2–3 个 pending = 未来 1~1.5 天的期望出分。不要在队列拥堵期把提交一次性打光。

## 10. 决策速查（给"当前分数 + 题型"，输出动作）

```
0 分 → 判 evaluation_error → 小包仍 0？→ 是：极限稳健版/换元数据；否：极简重做
45–65 → 题型：幻灯片/阅读/写作 → patch；图形 → 质量强化 v3；两者都先冒烟
65–78 → 同包重 roll 2–4 条（不回改包）
78+   → 低频重 roll；只保分
任一时刻发现"集体抬档" → 全量重提最佳包
最后 48h → 不改包；只重提；预留停止提交时间
```

## 11. 自检清单（每次提交决策前）

- [ ] 本次动作目的是"提分"还是"补覆盖"？两者不能混。
- [ ] 是否用的是**当前最佳包**（而不是一个未验证的新包）？
- [ ] 该题 pending 是否已 ≥2？超了就先等出分。
- [ ] 该题型是否适配本手段（图形题不用 patch、模板题不用融合）？
- [ ] 包/版本/trace 是否三件齐（可回滚、可重提）？
- [ ] 记录是否已写入（动作、时间、包版本、期望）？
