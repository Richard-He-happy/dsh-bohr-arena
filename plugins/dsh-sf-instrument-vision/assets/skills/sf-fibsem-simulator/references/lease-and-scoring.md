# lease 机制、分数解码与提交窗口

## 1. lease 申请参数（题面公开机制）

调试与自测通过 `POST /v1/leases` 申请模拟器 lease：

| 参数 | 取值 |
|---|---|
| `simulator_kind` | 固定 `fibsem` |
| `duration_minutes` | 推荐 10 |
| `scenario` | 按子题选择：`tilted-raw-v1`、`raw-sample-v1`、`offset-cross-v1`、`post-milling-v1`、`post-transfer-v1`、`needle-held-v1` |

- 申请后轮询状态，拿到连接信息（host/port/auth）即可操作；用完显式释放；失败重试必须跟踪到终态，避免残留 lease。
- 同一 scenario 每次 lease 的初态完全相同（确定性），因此可以离线标定「固定初态 → 目标位姿/参数」的常量，这是模拟器题可自动求解的基础。
- **答案包不申请 lease**：评测方为每个子题单独起 lease 并把 `FIBSEM_RPC_HOST`、`FIBSEM_RPC_PORT`、`FIBSEM_RPC_AUTH_TOKEN` 注入环境后执行入口。答案里申请 lease、写死控制器地址或夹带凭据都属违规。

## 2. 分数公式与解码

- 子题得分 `= 100 × A × (0.80 + 0.15V + 0.05E)`；合成分 `= 100 × Σ(子题得分/100) / 10 = Σ(子题得分)/10`。
- `V`：0 违规=1，每次违规 −0.25，最低 0；`E`：动作数 ≤ 参考+2 时为 1，之后每多 1 次 −0.1，最低 0；`A` 连续。
- **解码规则**：满分 100 的子题折算 10 分，所以合成分是 10 的整数倍 ⇔ 被评到的子题全部满分；出现小数 ⇔ 至少一个子题拿到部分分。把合成分 ×10 后拆成「×100 的整数部分 + 余数」，即可定位部分分来自哪一题（按入口顺序与已知锚点反推）。

| 观测合成分 | 解码 |
|---|---|
| 20.0 | 2 个子题被评到且满分 |
| 30.0 | 3 个 |
| 40.0 | 4 个（实现在 B01–B04 全满分时） |
| 48.5702 | 4×100 + B05 85.70176 |
| 0.0 + 2–9 分钟评测 | 0 个 lease：评测侧未真正执行 |

- 同一份答案多次提交分数会阶梯跳（10 的倍数），这不是答案变化，而是评测时成功启动的 lease 数变化。
- 反推 B05 的 A：85.70176/100 = A×(0.80+0.15V+0.05E)。若 V=0 需 A>1（不可能）⇒ V=1；取 E=1 ⇒ A≈0.857。

## 3. lease 容量与平台健康度

- 每个子题评测时都要起一个 simulator lease；容量/健康度不足时，评测按 B01→B05→G01→G05 顺序只跑到能跑的那几个，后段子题「未被评到」（记 0 但并非答案被判 0）。
- 实测容量阶梯：同一时段不同提交分别被评到 2/3/4/5 个 lease；换成真实 10 题全评需要约 10 个 lease 同时可用。
- 容量是**间歇放量（bursty）**的：连续探测同一 scenario 会出现一次成功、下一次 FAILED、再下一次成功。单次探测成功不能保证评测能起 5–7 个 lease。
- 结论：G 组在容量受限时基本轮不到；提高合成分最稳的路径是「前段入口全满分 + 第 5 个入口拿部分分」，而不是把额度赌在 G 组全过。

## 4. 故障判别（实测）

| 信号 | 正常 | 故障 |
|---|---|---|
| 评测时长 | 20–25 分钟（10 子题真实执行） | 2–9 分钟快速失败 |
| 分数 | 10 的整数倍或带部分分小数 | 0 分 |
| 同内容对照 | 同内容包稳定同分 | 同内容包一次 40、一次 0（决定性证据） |
| lease 探测 | acquire→ACTIVE→RELEASE 正常 | 503 / FAILED / 长时间 CREATING |
| 通用文案 | — | 「未找到完整、真实推导的解法」类模板文案（reward=0 的通用说明） |

- 故障窗口内的 0 分不代表答案有回归；不要据此回滚已验证内容。
- 平台可能对旧提交后台重评：创建时不正常、很久之后才出分；可只读查询历史提交状态作为恢复信号之一。
- 恢复信号：公开提交能正常出分（出现非 0 且评测时长正常）、lease 探测连续成功、失败窗口过去。

## 5. 提交窗口与额度管理

- 平台实际额度：每题 10 次/24h 硬上限（题面文字可能写得更宽）；额度窗口按平台公告时间结束，不用即作废。
- 平台按历史最高分保留 ⇒ 后续提交无下行；但仍不要把额度花在「同内容重交抽奖」上，除非内容已收敛且只剩容量这一个变量。
- 预算建议：1 发锚点确认 + 3–4 发单变量 + 2 发组合/巩固 + 2 发预留到窗口后段。
- 故障窗口不要提交：额度会消耗但拿不到有效分。先做只读监控（历史提交状态、公开出分、lease 探测），恢复后立即交。
- 窗口最后 2 小时若仍故障：优先确保「已验证的最优内容」已提交过一次；没有新证据就不改内容。

## 6. 最后一发决策树

```text
有已验证新改动（真机 E2E rc=0 + 指标对照）？
├─ 是 → 交新内容（单变量优先；平台取最高，无下行）
└─ 否 → 当前最高分内容是否已经提交过？
        ├─ 是 → 平台健康（评测时长正常/lease 探测成功）？
        │       ├─ 是 → 可同内容重交一次抽 lease 容量（仅剩容量这一变量时）
        │       └─ 否 → 等恢复信号；窗口结束前必须用掉额度
        └─ 否 → 立即交当前最优已验证内容（先保底）
```

- 判断「哪一版是当前最优」只认平台实测分，不认本地指标；本地指标只用于排除坏改动。
- 每次提交记录：内容 = 哪个候选目录、改动文件清单、预期分项、预期合成分、提交时间、出分时间与时长。

## 7. 可复用清单

- [ ] 答案包十个入口齐全、结构不变、改动文件可枚举。
- [ ] 无自申 lease、无凭据、无写死控制器地址。
- [ ] 提交前已知「当前最优内容」是哪一版、是否已提交。
- [ ] 知道如何用合成分反推被评到几个子题、是否有部分分。
- [ ] 故障窗口有判别标准（时长/同包对照/lease 探测）与恢复信号。
- [ ] 额度剩余量与窗口结束时间明确，最后一发留给已验证内容。
