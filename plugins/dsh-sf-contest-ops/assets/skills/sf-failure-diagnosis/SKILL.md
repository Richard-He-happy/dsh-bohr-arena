# 平台故障诊断与证据链

## 1. 用途与何时使用

比赛期间出现以下任一情况时，用它先判断"是答案问题还是平台问题"，再决定动作：

- 同一份内容前后提交分数差异极大（包括一次 0 分）。
- 某题全平台所有已评分尝试都是 0。
- 提交持续上传失败、队列长时间不动、评测快速失败。
- 回执出现 `evaluation_error` / `pending_review` / `submission_conflict` / `quotaExhausted`。

**第一原则**：不要用单次结果否定版本，也不要把平台 0 分当质量分。先拿证据，再动手。

## 2. 症状分类与判据

| 症状 | 典型判据 | 结论 |
|---|---|---|
| 上传失败/超时 | 提交直接报网络/超时；无 attempt 或 attempt 未入队 | 上传通道故障；不计分，恢复后重投同产物 |
| 快速失败（2–9 分钟出 0） | 正常评测需 10–60 分钟；同内容其它时间能出分 | 评测链路/租约容量故障，不是答案 0 分 |
| 同包不同分 | 两次提交的答题内容逐字节一致，分数/耗时差异大 | 评测条件差异（租约容量/评分器状态） |
| 全平台同题 0 分 | 他人公开 attempt 同样全 0；同批其它题正常出分 | 该题 grader 未生效/故障 |
| 分数偏低但稳定 | 本地 scorer 与平台分可对齐，分项一致 | 真实分；从内容/口径入手 |
| `evaluation_error` | 评测侧失败，可能不消耗额度 | 先等自动重评（约 30 分钟），不要急重交 |
| `submission_conflict` | attempt 已绑定其它 bundle | 新建 attempt 重投 |
| `quotaExhausted` | 配额用尽 | 停手，冻结候选 |

## 3. 诊断流程

```text
拿到异常回执
  → 1. 看评测耗时：异常短 = 评测没真正跑
  → 2. 看分项/子题：全 0 还是有分项？
  → 3. 与同内容历史 attempt 对比（逐字节/哈希）
  → 4. 看同题公开 attempt 是否正常出分
  → 5. 看同批其它题是否正常（区分单题故障 vs 平台故障）
  → 6. 本地官方 scorer 复算：本地是否正常
  → 结论：答案问题 / 通道问题 / 评测故障 / 评分器故障
```

动作对照：

| 结论 | 立即动作 | 后续动作 |
|---|---|---|
| 答案问题 | 改包（一次一个变量） | 本地验证后重投 |
| 通道问题 | 重投同产物（不消耗额度时） | 恢复后批量补投 |
| 评测故障（租约/链路） | 保留最优产物，等恢复 | 恢复后同内容重投（可能更高分） |
| 评分器故障（全 0） | 保留合规产物 + 证据链 | 修复后立即重提，往往直接拿真实分 |
| 额度用尽 | 冻结最优候选 | 等下期/新窗口 |

## 4. 证据链模板（用于申诉/复盘）

1. **时间线**：故障开始/结束时间、关键提交时间、恢复信号时间。
2. **同内容对照**：同一答题内容在故障前后两次提交的回执（分数、耗时、状态），附"内容一致"的证据（本地对包哈希/逐字节比较的结论，不要粘贴长哈希）。
3. **平台侧对照**：同题其他公开提交是否正常；同批其他题是否正常。
4. **本地复算**：本地官方 scorer 的分数与分项，证明产物本身合规。
5. **产物合规材料**：契约检查清单（字段/行数/ID 唯一性/取值域）、复现命令、方法说明。
6. **诉求**：请求重评/补分/确认 grader 状态；给出可核对的最小材料路径（不含个人信息）。

## 5. 恢复后的动作优先级

1. 先单条探测（小包/最优包）确认通道与评测恢复。
2. 恢复后第一波集中重提"已验证最优包"（故障期被误判的 attempt 可能吃不到重评）。
3. 若平台支持自动重评，先等满一个重评窗口再决定是否新建 attempt。
4. 记录恢复前后分数对照，作为后续复盘证据。

## 6. 常见误判

| 误判 | 后果 | 纠正 |
|---|---|---|
| 把 0 分当"版本差" | 浪费额度重做 | 先看耗时与全平台情况 |
| 故障期频繁重交 | 额度耗尽、队列更堵 | 暂停提交，保留产物 |
| 把"自己做不到"当"别人违规" | 错过合法方法 | 先逆向高分方案/找允许的数据源 |
| 用单次低分否定版本 | 丢掉有效设计 | 同包重交 2–3 次再判断 |
