# 配额规划失误复盘（脱敏）

> 目的：把"有限提交次数下没有规划好次数"变成可执行的规则，而不是一句口号。
> 数据口径：只保留"几次/几条/相对分差"，不含任何内部 ID 与身份信息。

## 1. 结果层面

- 7 道主赛题中，多数在 24 小时窗口内打满约 10 次计分提交额度。
- 至少 3 道题出现"后期已有验证过的候选，但额度已耗尽无法提交"或"最后一发没有用于改进"。
- 这些题的最终分与"已有候选的潜力"之间存在明显差距；额度问题直接限制了上限。

## 2. 典型场景（按题类型）

### 2.1 视觉组合题：前期试错 + 后期无额度

- 前期约 3 发用于未验证的早期版本（"先交一版看看"）。
- 后期训练/推理侧改进产出约 10 个经过本地验证的候选（本地分从 55 到 59 不等），额度已用尽，全部无法提交。
- 最终分停在"最后一次提交"的结果上，而不是"已验证最好的候选"。

**教训**：验证在本地，提交只花在"已验证且能改变决策"的候选上。

### 2.2 模拟器/交互题：故障窗口消耗额度

- 前期约 5 发落在评测服务/租约故障窗口：快速失败或只评到部分子题，未拿到有效分，却消耗了额度。
- 后期评测恢复时额度已紧张，只能优先保证"内容最优"的最后几发。

**教训**：提交前先判平台健康；故障窗口只备候选，不提交。

### 2.3 预测题：最后一发的决策价值

- 最后一发额度被用于"同内容探测"（想观察评分/评测条件），但没有带来任何提升。
- 该题距更高档位只差约 1.6 分；如果最后一发用于提交一个已验证的新候选，结果可能不同。

**教训**：最后一发的标准是"已验证的新候选或已验证最优包"，不是"再抽一次"。

### 2.4 全新题：评分器未生效期间消耗额度

- 某题评分器未生效时，全平台同题所有已评分尝试都是 0 分；期间多次提交也都是 0 分（非答案问题），消耗了额度。
- 评分器修复后立即重提，拿到真实高分（0 → 90+ 的阶梯）。

**教训**：全平台同题 0 分 = 评分器/评测故障；保留合规产物，等修复后重提，不要在故障期反复提交。

## 3. 根因分析

| 根因 | 具体表现 | 修正 |
|---|---|---|
| 额度不是预算 | 没有为"锚点/探针/组合/预留"分配次数 | 赛前写预算表，按表执行 |
| 用提交代替验证 | 未验证版本直接提交 | 本地官方 scorer 判分 + dry-run |
| 不识别故障窗口 | 故障期按正常窗口提交 | 提交前做健康检查（公开尝试/耗时/队列/租约） |
| 最后一发无标准 | 把额度当"抽奖" | 明确定义：已验证新候选 > 已验证最优包 > 不用（兜底除外） |
| 没有台账 | 凭记忆判断额度与版本 | 全程台账：版本/本地分/平台分/额度余量 |

## 4. 正面样板：工程型题

- 三题格式解析：先本地复刻官方验收器，批量生成/加固后在本地全量判分，只把"本地已验证提升"的版本提交。
- 结果：三题都在额度内拿到接近上限的分数，没有出现"有候选无额度"。
- 关键差异：**每发提交都有本地证据支撑**，提交是"确认"而不是"探索"。

## 5. 可执行规则（下期）

1. 开赛前写每题额度预算：`锚点 1 + 单变量 4~5 + 组合 2 + 最后预留 2~3`。
2. 提交前三分支检查：本地验证过？能改变决策？余量够最后阶段？
3. 平台健康检查通过才提交；故障窗口 0 发。
4. 最后 2 小时只做"已验证最优包/新候选"的提交；不探测、不实验。
5. 全程台账；每 2 小时复盘一次"额度用了多少、还剩多少、最后预留是否安全"。
6. 若额度提前接近耗尽：停止一切探索性提交，把剩余额度留给"已验证最优包 + 同内容重提交博取评测条件"。
