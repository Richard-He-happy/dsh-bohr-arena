# 限时科学竞赛平台机制（评分、额度、队列、租约）

## 1. 用途与何时使用

- 第一次参加玻尔 Playground 类限时竞赛，需要先搞清"分数从哪来、提交怎么走、什么情况会白交"。
- 比赛进行中遇到出分慢、同包不同分、全平台 0 分、提交被拒，需要按机制定位原因。
- 制定提交计划前，用它把平台约束换算成"预算表"。

本技能只讲平台机制，不讲具体题目的科学方法。题级打法见对应场景技能。

## 2. 评分链路：三个乘数

平台侧真实评分（与题面 `scoring` 字段可能不一致，以实测回执为准）：

```text
score = 100 × harbor_reward × trace_factor
```

| 因子 | 含义 | 实测要点 |
|---|---|---|
| `harbor_reward` | 评测器按题面 metric 算出的原始奖励，通常 0–1 | 本地复刻官方 scorer 后应能对齐（误差 <0.1）；对齐前不要相信本地分数 |
| `trace_factor` | trace 质量门控系数 | 太短/不可读的 trace 会被乘 0 或重罚；工程上按"trace 分 ≥70 才能拿满系数、<30 直接 0"来要求自己 |
| `100` | 百分制缩放 | 队内汇报统一用平台分，不用原始 reward |

**判据**：拿到回执后先看 `harbor_reward` 与 `trace_factor` 是否能解释总分；解释不了时优先怀疑评测链路（见 §5），而不是继续改答案。

## 3. 提交通道：必须走 CLI 的 ARM bundle

- 提交物 = **ARM bundle**：输出文件 + 真实 Agent 原生会话 trace + manifest。
- 必须用官方 Playground CLI 提交（`playground submit`）。平台 API 直接"绑定一个已有 attempt 的 bundle"到不了 Harbor worker，attempt 会长期停在 scoring/queued，最终 0 分——这是最容易踩的"通道死法"。
- 上传失败 ≠ 计分失败：上传失败通常不消耗提交额度，修好后重投同一产物即可。
- bundle 有体积上限；输出目录含大量中间产物时，CLI 打包会把 outputs 复制成 results，体积翻倍，容易触发 worker 拒收。提交前先瘦身（去掉重复副本），并记下瘦身后的字节数。
- trace 必须是**真实、完整、未编辑**的原生 Agent 会话 JSONL；提交前跑 `playground trace validate`，必须 `valid: true`。不伪造、不裁剪、不删日志、不倒填时间戳。

## 4. 提交额度与评分队列

| 机制 | 实测行为 | 对策 |
|---|---|---|
| 每题计分额度 | 通常 **10 次/题/24h**，按账号计（同一账号绑定的多个提交共用一个池） | 把额度当预算表：锚点 1 发 + 单变量探针 4–5 发 + 组合 2 发 + **预留 2 发**给最后 2 小时 |
| 题面与平台冲突 | 题面可能写"提交不限次数"，但平台仍按 10 次硬限拒绝 | **以平台实际返回的配额字段为准**，不要按题面文字做计划 |
| 429 `quotaExhausted` | 额度用尽，不会再评测 | 停手；把剩余候选冻结，等下期/重开配额 |
| 409 `submission_conflict` | 该 attempt 已绑定别的 bundle 哈希 | 新建 attempt 重投，不要复用原 attempt |
| 评分队列 | 提交后 `queuePosition` 常数百到上千，出分 10 分钟–数小时；故障后积压更久 | 早交早排队；按"在队数量 = 未来若干小时出分弹药"管理；每 2h 轮询一次即可，不要高频重投 |
| 失败码 | `evaluation_error` 是评测侧失败，可能不烧额度 | 先等平台自动重评（约 20–40 分钟），不要立刻重交；确认不会重评再新建 attempt |

## 5. 评测租约容量（模拟器/交互类题的关键机制）

部分题目由评测方为**每个子题单独启动一个模拟器 lease** 并注入运行时参数。此时：

```text
分数 ≈ 10 × 成功启动 lease 的子题数 × 子题质量
```

- 评测按子题顺序进行；**能同时/依次成功启动的 lease 数决定有多少子题被真正评到**。没轮到的子题不是"被判 0"，而是"从未被评测"。
- 观测量：同一份答案在不同时间提交会出现 20/40/48.57 这种阶梯式分数；评测耗时异常短（2–9 分钟，正常需 10–60 分钟）通常意味着 lease 起不来、0 个或少数子题被评。
- 对策：① 把高价值/必做子题放在评测顺序前面；② 先小规模提交探明"当前能起几个 lease"；③ 最后阶段用已验证最优内容多提交一次，博取更高的 lease 容量（同一账号取历史最高分，无下行风险，前提是额度允许）。
- lease 探测：在允许的范围内观察 lease acquire/release 成功率，可以判断评测服务是否健康；bursty（间歇成功）说明容量紧张，不要把提交窗口与健康窗口错配。

## 6. 平台故障的语义与判定

| 现象 | 判定 | 动作 |
|---|---|---|
| 提交包上传超时/失败 | 上传侧故障 | 不算计分；恢复后重投同一产物 |
| worker 502 / 连接超时 | 评测 worker 不可用 | 暂停提交，保留产物；恢复后集中重提 |
| 同一内容两次提交分数差极大（含一次 0） | 评测链路失败或租约容量差异 | 先看评测耗时与回执；不要把 0 当质量分 |
| 全平台同题所有已评分尝试都是 0 | 该题 grader 未生效 | 保留合规产物+证据链；等修复后立即重提（可能直接拿真实分） |
| 平台自动重评 | evaluation_error 后常见 | **先等自动重评**，约 30 分钟内可能救回；不要急着重交浪费额度 |

任何"平台故障导致低分"的结论都要有证据：同内容不同时间对照、逐字节/哈希一致的包、评测耗时、同期其它 attempt 是否正常。见 `sf-failure-diagnosis`。

## 7. 合规红线

- 只使用题面允许的数据与工具；不使用测试标签、隐藏真值、文件名回查等泄漏信息。
- trace 真实、完整、未编辑；产物可复现；日志不删不改。
- 不用平台 API 绕过 CLI 提交；不改名/覆盖他人产物。
- 成绩记录优先于边际分数：不确定合规的"兜底技巧"宁可不做。

## 8. 自检清单（开赛前）

- [ ] 已用 CLI 成功提交过一次探针，知道回执里看哪些字段（status / scoringState / quota / bundle 大小）。
- [ ] 已用真实 Agent 会话跑通 `trace validate`。
- [ ] 已确认每题额度与题面是否冲突，并写出每题预算表。
- [ ] 已确认评分 metric 与本地 scorer 的对齐方式（至少一个参考点）。
- [ ] 知道当前题目是否属于"每子题起 lease"的类型，以及子题顺序。
- [ ] 已准备瘦身 bundle 与最终产物冻结流程。
