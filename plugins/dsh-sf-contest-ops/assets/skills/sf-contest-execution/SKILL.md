# 24 小时短赛执行手册

## 1. 用途与何时使用

- 比赛开始前 1–2 天：按赛前清单准备，避免开赛后才摸平台。
- 开赛瞬间：按 T0 检查单确认状态、按优先级发首波提交。
- 比赛进行中：按固定循环推进"提交→收分→改进→再提交"，并管理额度与队列。
- 最后 2 小时：冻结改动、收尾、确认最终成绩。

单人/多 Agent 团队都适用；团队协作要点见 `references/team-division.md`。

## 2. 赛前准备（T-2 天 ~ T-1 小时）

| 项 | 要求 | 产出 |
|---|---|---|
| 平台机制 | 读完题面/文档；确认评分 metric、提交方式、额度、trace 要求 | 一页机制表 |
| 提交链路 | 用真实 Agent 会话跑通 trace validate + dry-run + 一次真实探针（若平台允许赛前提交且不占额度） | 可复现的提交脚本 |
| 题目资源 | 下载题面、资源包、公开样本、参考基线；确认数据边界与禁用项 | 只读材料目录 |
| 评分复刻 | 复刻官方 scorer/判分逻辑；用参考解或常数基线校准（误差 <0.1） | 本地判分脚本 |
| 基线产物 | 每题准备一个"能跑通、能拿保底分"的基线 | 冻结的 baseline |
| 环境 | 依赖、编译/运行环境、GPU/工具链、超时与日志 | 环境自检脚本 |

原则：**开赛前把"通道"跑通，开赛后只做科学改进**。通道问题在 24h 赛制里代价极大。

## 3. 开赛瞬间（T0 ~ T+30 分钟）

1. 确认每题状态（open/roundStart/roundEnd）、本轮规则、`countsTowardQuota` 是否已变为 true。
2. 重新拉一次题目配置与公开榜单，记录当前公开最高分/中位线（只用于判断量级）。
3. 按"已就绪程度 × 期望分/时间"排序，**先发已冻结的基线**占住位置（评分队列长，早交早出分）。
4. 建立评分轮询（每 10–15 分钟扫一次全部 attempt）。
5. 记录首波提交台账；确认回执字段与额度计数符合预期。

首波提交顺序建议：

```text
1) 全新题/只有你在做的题 → 先交先有
2) 已冻结基线的题       → 拿保底分、验证通道
3) 高价值组合题         → 按"最稳子题在前"排列入口
4) 大包/上传有风险的题   → 先瘦身再交，避免占用开赛窗口
```

## 4. 24 小时节奏（T+30 分钟 ~ T-2 小时）

固定循环（单题 60–90 分钟一轮，多题并行）：

```text
00–05  轮询：每题最新 attempt 的状态/分数/分项
05–15  决策：看差距与方差，决定"重交最优包"还是"改一个变量"
15–45  改进：一次只改一个因素，本地官方 scorer 验证
45–55  真实 Agent 会话复跑关键步骤，采集原生 trace
55–65  dry-run；通过后真投（每轮 2–4 条，避免队列拥堵）
65–90  继续下一轮；不等分
```

提分优先级（通用）：

1. **P0 修 0 因**：产物路径/格式/契约不符、trace 不可用、包缺件 → 立刻修（0→有分）。
2. **P0 口径修正**：metric 公式、匹配规则、单位、字段语义 → 可能一次 +10~40。
3. **P1 主指标**：题目权重最大的子项/子题（通常占 30–80%）。
4. **P2 组合增强**：TTA、后处理、多模型融合（必须在单变量验证有效之后）。
5. **P3 文档/证据**：method.md、可复现记录（低成本，评审可见）。

## 5. 额度与队列纪律（本轮最大教训）

> **本轮最严重的失误：有限提交次数下没有规划好配额。** 多数题打满约 10 发，出现"已验证候选准备好了却无额度可交"；个别最后一发被用于探测而不是改进；还有多发起落在评测故障窗口、没拿到有效分却消耗了额度。详见 `sf-round-lessons` 与 `references/quota-postmortem.md`。

- 赛前为每题写额度预算表：锚点 1 发、单变量探针 4–5 发、组合 2 发、**最后 2 小时预留 2–3 发**。
- **每发提交前问三个问题**：① 这个改动本地验证过吗？② 这一发能改变什么决策？③ 余量还够最后一小时吗？三问有一个"否"就不交。
- 不要用额度做"验证/探测"：dry-run 与本地 scorer 才是验证手段；"同内容探测"只在明确需要博取评测条件时使用，且不得占用最后预留。
- 平台故障窗口 0 发：先做健康检查（公开尝试是否正常出分、评测耗时、队列、租约探测），确认健康再交。
- 评分队列拥堵时（队列位置长时间不动、失败率升高）：只备候选，不密集提交。
- 同题同日提交不要超过约 6 次；边际收益递减且加剧拥堵。
- 全程记台账（版本/本地分/平台分/额度余量）；每次提交前看一眼台账，不要凭记忆。

## 6. 最后 2 小时

1. 停止改科学代码与包结构。
2. 每题把"已验证最高 reward 的产物 + 最完整 trace"做最终提交（若还有额度）。
3. 确认所有最终 attempt 为 scored；记录最终分数、分项、回执。
4. 若平台故障：按截止时间兜底提交最稳版本，并记录故障证据。
5. 20 分钟前完成最后一次核对：分数、排名区间的量级、最终产物清单。

## 7. 常见失败模式

| 失败 | 原因 | 对策 |
|---|---|---|
| 首波提交太晚 | 开赛后才摸通道 | 赛前跑通探针；T0 先交基线 |
| 额度在前期耗尽 | 无效版本多次提交 | 单变量探针 + dry-run；预算表 |
| 改进无法归因 | 一次改多个因素 | 一次只改一个变量 |
| 被评分队列拖死 | 高频重投 | 固定 2h 轮询；按在队数量管理 |
| 团队并发提交冲突 | 多人同时提交同一题 | 单点提交（一人/一个脚本持锁） |
| 最后没交最优版 | 忘了预留额度 | 最后 2h 预算硬预留 |
