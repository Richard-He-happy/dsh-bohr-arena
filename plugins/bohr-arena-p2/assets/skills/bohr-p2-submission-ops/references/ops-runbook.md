# 提交运维手册（ops-runbook）

> 配套 `bohr-p2-submission-ops` 的 SKILL.md。这里放可照着执行的命令级细节、解析容错、状态轮询、失败恢复、排名计算与记录模板。
> 所有命令用占位符表示（`<DIR>`、`<FILE>`、`<VERSION>`），不写死固定路径。

## 1. 打包（pack）

### 1.1 目录约定

```
<workspace>/
  candidates/<VERSION>/submission/      # 唯一要提交的内容
  candidates/<VERSION>/trace/           # 原生会话轨迹（不打包进 submission）
  work/                                 # 中间文件，不提交
```

### 1.2 打包白名单

只打 `submission/` 下的文本资源：`SKILL.md`、`scripts/**`、`resources/**`、`references/**`、`templates/**`、`examples/**`（示例须标注"示例，非正式案例结果"）。

明确排除：`__pycache__`、`*.pyc`、`.venv`、`.git`、`.DS_Store`、`*.log`、示例 PDF 与大二进制、任何凭据文件、旧版本目录、`work/`。

### 1.3 打包前脚本化检查（建议写成一次性脚本）

1. `submission/SKILL.md` 存在（否则直接中止）。
2. 解析 SKILL.md 中的相对路径引用，逐个 `Test-Path`/`os.path.exists`；缺失即中止。
3. 文件数 ≤50、单文件 ≤500KB、总计 ≤2MB（留余量：bundle 通常是 outputs 的 2–3 倍）。
4. 无缓存/无二进制（按扩展名白名单反向检查）。
5. 打印清单与总字节数，人工扫一眼是否混入基线目录/旧版本文件。

### 1.4 常见打包坑

- **自动前缀检测误选基线目录**：自动识别不可靠时显式指定前缀，或手工 staging 后核对顶层目录名。
- **含中文的脚本/提示写入**：在 Windows 上要用"无 BOM 的 UTF-8"；带 BOM 会让目标环境的首行解析失败。读取时显式指定 UTF-8，不要依赖系统默认编码。
- **两份 SKILL.md 不一致**：只保留提交根目录一份正式入口；如保留副本必须逐字一致。

## 2. 提交（submit）

### 2.1 提交前

```
playground --version            # 确认最新；有更新先升级
playground trace validate <TRACE_FILE>   # 轨迹可读性预检
```

### 2.2 提交

```
playground submit --outputs <DIR> --trace <TRACE_FILE> --model <MODEL> --harness <HARNESS>
```

- `--trace` 用 Agent 原生会话文件；没有原生会话时不要用"两条消息"合成 trace（二期实测合成 trace 大量 failed）。
- `--model` 字段有长度限制（二期实测超过约 40 字符会触发字段超长拒绝），提交前先截断/确认。
- 返回 `queued` + 任务标识 = 入队成功。**入队后不要重复提交同一包催分**。

### 2.3 stdout 污染的处理

旧版 CLI 会在 JSON 前后打印版本警告，导致按 JSON 解析失败：

```powershell
$raw = & playground status --json 2>$null | Out-String
$start = $raw.IndexOf('{')
$json = if ($start -ge 0) { $raw.Substring($start) | ConvertFrom-Json } else { $null }
```

或先剥离警告行再解析；解析失败时打印原始输出前 200 字符用于诊断，不要静默当"无数据"。

## 3. 状态轮询

### 3.1 轮询逻辑（伪代码）

```
每 1–2 小时：
  records = 拉取本轮所有提交的状态
  for r in records:
    if r.status in (queued, evaluating, provisional): continue
    if r.status == scored: 记录分数；更新"版本→分数序列"
    if r.status in (failed, pending_review): 标记通道失败，不计入版本优劣
  重算：每题历史最佳分、实时门槛、差距
  输出本轮动作建议（重 roll / 小补丁 / 换题 / 停手）
```

### 3.2 轮询纪律

- 只读，不写；不要在轮询脚本里顺手提交。
- 每次记录"提交时刻 → 状态变化时刻"，用于估算当前出分延迟。
- 发现连续多条 failed 且同批其他人正常出分 → 优先查 trace 与包体，不要归因于内容质量。
- 队列长时间不动时，降低轮询频率，避免被平台限速。

## 4. attempt 状态机与恢复决策树

```
                  ┌─ scored ──────────────► 记录分数，进方差分析
queued → evaluating ── failed ─────────────► 通道失败：间隔后新建 attempt
                  └─ pending_review ───────► 终态：换包/换 trace 再提交
```

决策树：

1. 状态 `failed` → 检查 trace 是否可读、包是否完整、CLI 是否最新；修通道后**新建 attempt**。
2. 状态 `scored` 但分数远低于历史区间 → 先同包重投 2–3 次；仍低再归因版本。
3. 带旧 attempt 重跑返回失败 → 不允许修旧 attempt，必须新建。
4. 同一包连续 3 次 failed → 停止该包，改 trace 来源或重打包。

## 5. 失败恢复表

| 症状 | 最可能原因 | 恢复动作 |
|---|---|---|
| 提交后很快 failed | trace 不可读/过短/合成 | 换原生会话文件；先 validate |
| 提交被拒（字段类错误） | 字段超长或格式不符 | 缩短/修正字段后重提 |
| 提交返回 502 | 上传通道故障 | 重试 1–2 次；间隔后再试；保留本地候选 |
| 包上传后评测异常 | 包体过大/文件类型异常 | 清理资源、去掉二进制；留出体积余量 |
| 长时间 queued | 队列拥堵 | 等待；只备候选不密集提交 |
| 出分整体偏低 | 平台校准漂移 | 与同时段其他提交对比；不要改好版本 |
| 状态长时间不更新 | 轮询/解析问题 | 检查 stdout 污染、接口是否变更 |

## 6. 排名与差距计算

```
1) 每人取历史最佳分（只算 scored）
2) 降序排序，得到门槛分（第 5 名那个位置的分）
3) 名次 = 1 + 最佳分严格高于自身的人数
4) 差距 = 自身最佳分 − 门槛分
```

注意：

- 并列同分共享名次；门槛把并列者一起算进去。
- 不要混入 failed/pending 的分数，也不要用 attempts 数量当排名依据。
- 门槛随时间上涨（过夜常见 +1~+5）；每次轮询都重算，不缓存旧门槛。
- 差距 >5 分的题，重 roll 的期望收益趋零，应停止追投。

## 7. 记录模板

### 7.1 版本记录（每题一张）

| 版本 | 结构变化（文件数/脚本数/新增资源） | 提交次数 | 分数序列 | 结论 |
|---|---|---:|---|---|
| v1 | 14 文件 / 1 脚本 | 3 | 72 / 72.33 / 76 | 精简版，保留 |
| v2 | 27 文件 / 5 脚本 | 1 | 67.67 | 加功能掉分，弃用 |

结论只写"保留/弃用/待验证"三种，避免凭印象。

### 7.2 轮次记录（每轮一行）

| 时刻 | 提交数 | 入队 | 出分 | failed | 本轮最高分 | 门槛变化 | 下轮动作 |
|---|---:|---:|---:|---:|---|---|---|

## 8. 节奏与停止条件

- 首日先铺基线（每题的稳定版本各 1 条）。
- 之后每轮 2–4 条；同题一天 ≤6 条；总提交数与队列健康度挂钩。
- 停止条件（满足任一即停）：门槛已超出差距上限；同一版本连投 5 次无上尾；赛程剩余时间不足一轮出分；平台长时间停滞。
- 保位优先：已在高位的题只做低频重 roll，把提交次数留给差距小的题。

## 9. 红线

1. 不伪造/拼接轨迹；不复用被拒的 trace。
2. 不把示例输出当正式结果提交；不提交预制答案。
3. 不把凭据、身份信息、内网地址写进包、trace 或提交字段。
4. 不一次提交 8–10 条；不在队列拥堵期密集提交。
5. 不用旧门槛做决策；不因单次低分删掉历史最好版本。
