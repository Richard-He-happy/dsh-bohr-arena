# 玻尔 Playground 提交与评测机制（operating manual）

## 1. 用途

**用**：在玻尔 Playground 产品赛里打包、提交、查分、排障、算差距、定节奏。
**不用**：写 Skill 内容（→ `bohr-p2-skill-blueprint`）、逐题配方（→ `bohr-p2-task-playbooks`）、赛制全景（→ `bohr-p2-overview`）。
**一句话**：提交 = 打包产物 + 可读取的轨迹证据；分数 = 版本质量 + 评测方差；节奏 = 用有限提交次数换"上尾"。

## 2. 提交流程总览

```
候选包目录 → 打包（只含 submission/） → trace 校验 → submit → 入队确认 → 轮询出分 → 记录 → 决定 next
```

提交命令的语义（题面/CLI 公开）：`playground submit --outputs <DIR> (--trace <file> | --raw-messages <file>) --model <name> --harness <name>`。

- `--outputs` 指向包含 `submission/`（或直接是产物目录）的目录；**入口必须是 `submission/SKILL.md`**。
- `--trace` 必须是**真实 Agent 会话轨迹**；`--raw-messages` 是原始消息记录。两者都要能被平台完整读取。
- 返回 `queued` + 任务标识即证明入队成功；之后只能等，不能"重发加速"。

## 3. CLI 版本维护

- 平台会检查 CLI 版本；旧版会在输出里打"已过期，可能影响分数"之类的警告。二期实测：从 0.1.48 升到 0.1.49 后警告消失、JSON 输出恢复正常。
- **警告文本会污染 stdout**：旧版把警告混进 JSON 前后，脚本按 JSON 解析时会误判"全部未出分"。
- 解析容错两条：① 把 stderr 单独丢弃（如 PowerShell 下 `2>$null`）；② 从输出中截取第一个 `{` 到最后一个 `}` 再解析。
- 提交前固定动作：`playground --version` 确认版本；有更新先升级再提交。

## 4. trace 准入（二期最大的一次翻车点）

| 事实 | 数据 |
|---|---|
| 用"prompt + answer 两条消息"合成的 conversation-record 作 trace | 一批 11 条提交中 **7 条 failed**（evaluation_error） |
| 改用 Agent 原生会话文件（如 Codex 的 rollout JSONL） | 后续 15+ 条提交 **0 failed** |
| 提交前用 `trace validate` 预检 | 能提前判断能否被平台读取 |

要点：

1. **trace 必须真实**：平台对"可完整读取"的要求变严，过短/合成/结构不完整的轨迹会直接失败。不要伪造、不要拼接。
2. **首选 Agent 原生会话文件**：一次真实会话的完整事件流（含工具调用）最稳。
3. **把"提交前最终校验"与 trace 生产合并**：让 Agent 在候选包目录里读题面、检查引用、跑 `--help`/自检、修小问题，这个会话本身就是可提交的 trace——既真实，又能顺手修包。
4. trace 里不要出现凭据、身份信息、内网信息。

## 5. attempt 状态机

```
queued → evaluating → provisional → scored        （成功路径）
queued → evaluating → failed                       （评测失败，终态）
queued → evaluating → pending_review               （待审，终态）
```

- **`failed` / `pending_review` 是终态**：不会自动恢复。
- `--attempt-id <旧 id> --bundle <包>` 的"重试"**不会重新入队**，返回 `evaluation_failed`；要拿新分只能**新建 attempt**（重新 submit）。
- `failed` 不等于低分：不要把它计入版本优劣，也不要因 failed 就改包——先隔一段时间用同包重投。
- 记录每次提交：版本名、提交时刻、状态、分数。区分"通道失败"与"质量低分"。

## 6. 评测方差与重 roll

- **同一份包重复提交，分差常见 8–15 分**（二期多题实测：同一题的最高分与最低分差可达 11–18 分）。分数上限更像"抽到的上尾"。
- **重 roll 是唯一被反复验证的提分手段**：把历史最好版本原样重投 3–5 次取最高；对差距 ≤2 分的题收益最高。
- **单次分数不能判定版本**：至少 3 次同包重投再判断；同包低分先归因于方差。
- **平台校准会整体漂移**：某段时期整体下移约 5 分（不同版本、不同题同时下降）。此时不要用"历史门槛"直接对比当前提交，要看同一时段的相对位置。
- **不要用低分覆盖心理预期**：榜单按历史最好分保留，新版本只用于冲高，不删旧版本记录。

## 7. 并列感知排名

平台按"每位选手的最佳分"排名。正确算法：

```
名次 = 1 + (最佳分严格高于自己的选手数)
```

- 并列同分共享名次，不重复占位。
- 数据口径：**按作者取最佳分**、**只统计已完成（scored）的提交**、排除失败/待审。
- 不要用 attempts 列表直接排序冒充榜单（同一人多条 attempt 只取最佳）。
- **门槛会涨**：第 5 名门槛随对手提交持续上涨（过夜常见 +1~+5 分）；要用实时门槛算差距，不要用几天前的数字做判断。
- 规划口径：差距 = 自身最佳分 − 当前门槛；差距 ≤2 分才值得集中重 roll。

## 8. 队列拥堵与节流

| 现象 | 判断 | 处理 |
|---|---|---|
| 提交 1–4 小时出分 | 正常 | 每小时检查一次即可 |
| 队列长时间不动（曾持续约 8 小时） | 平台拥堵 | 停止连续补交，只准备候选 |
| 拥堵期失败率明显上升、分数普遍偏低 | 评测质量下降 | 不把拥堵期的分当版本结论 |
| 提交后立刻 `queued` | 入队成功 | 不要重复提交同一包"催分" |

节流规则：

- 每轮提交 **2–4 条**；同一题一天不超过约 **6 条**。
- 不要一次提交 8–10 条：加剧拥堵、拉长出分时间，且评测方差更大。
- 拥堵期"只备候选、不密集提交"；恢复后（队列位置快速下降、失败率回落）再投。
- 优先保位（已是高分的题）→ 再冲差距小的题 → 大差距题只做新设计。

## 9. 提交前 / 提交后清单

**提交前（缺一不可）**：

- [ ] `submission/SKILL.md` 存在且 frontmatter 合法；引用文件全在包内；
- [ ] 无 `__pycache__`、无大二进制、无凭据；文件数/体积在限内；
- [ ] 每个脚本 `--help` 或自检入口退出码 0；空输入能产出合法 `result.json`；
- [ ] `result.json` 16 字段、`output_contract` 原样回填；
- [ ] `trace validate` 通过（或至少确认 trace 是可完整读取的原生会话文件）；
- [ ] `playground --version` 为最新；
- [ ] 记录本轮版本名与改动点，便于出分后归因。

**提交后（每轮）**：

- [ ] 确认返回 `queued` 并入队；
- [ ] 把提交写进记录表（版本/时刻/状态）；
- [ ] 出分后先看失败还是低分：failed → 通道问题，低分 → 方差或质量；
- [ ] 重算实时门槛与差距，决定"继续重 roll / 打小补丁 / 换题 / 停手"；
- [ ] 更新"版本 → 分数序列"，不因单次低分删版本。

## 10. 常见故障处置

| 故障 | 现象 | 处置 |
|---|---|---|
| trace 不可读 | 大量 `failed` / evaluation_error | 换 Agent 原生会话文件；提交前先 validate |
| CLI 过期 | stdout 有版本警告，JSON 解析失败 | 升级 CLI；解析时截取 JSON 段 |
| 队列停滞 | 长时间 `queued`/`evaluating` | 等待 + 只备候选，不连续补交 |
| 上传通道故障 | 提交返回 502 一类错误 | 重试 1–2 次；仍失败则隔一段时间再试，同时保留本地候选 |
| 字段超长 | 提交被拒（如 model 字段超过约 40 字符） | 缩短字段值后重提 |
| 包体过大 | 上传/评测异常 | 清理无用资源；bundle 体积通常是 outputs 的 2–3 倍 |
| 重试不入队 | 带旧 attempt 重跑返回失败 | 新建 attempt（重新 submit），不要修旧 attempt |
| 合成 trace 被判失败 | 提交后立刻 failed | 改为真实会话 trace；不要复用被拒的 trace |

## 11. 节奏模板（可直接照着排）

| 时间 | 动作 |
|---|---|
| 首日 | 10 题各交 1 版精简骨架，拿基线分；确认通道与契约没问题 |
| 第 2 天起 | 每 1–2 小时检查出分；每轮 2–4 条重 roll；按实时差距排序 |
| 差距 ≤2 分 | 集中重 roll，每轮 2–3 条 |
| 差距 2–5 分 | 重 roll 1–2 条 + 一次最小补丁（+≤3 文件 / +35KB / +1 脚本） |
| 差距 >5 分 | 停止追投，只做新设计或换题 |
| 停手 | 门槛涨过差距上限、连投 5 次无上尾、或赛程剩余时间不足一轮出分 |
