# 提交前自检清单（selftest-checklist）

> 用法：每次改版、每次打包、每次提交前逐组执行。A–D 为打包前必过项，E–G 为提交前终检。
> 原则：**能脚本化的不要靠人看**；每条都给出可观察的判断依据，而不是"检查一下"。
> 二期实测：大量 0 分/`evaluation_error` 都由本清单 A、B、C 三组问题造成，而非内容质量。

## A. 布局与打包（5 项）

- [ ] 入口文件在提交根目录：`submission/SKILL.md`；包里不存在第二份内容不一致的 SKILL.md。
- [ ] `SKILL.md` 里出现的每个相对路径（`scripts/…`、`resources/…`）都在包内存在。
- [ ] 无 `__pycache__`、`.pyc`、`.venv`、`.DS_Store`、大二进制、示例 PDF、日志、凭据文件。
- [ ] 文件数 ≤50；单文件 ≤500KB；总计 ≤2MB；无符号链接。
- [ ] 打包工具没有误选基线目录（自动前缀检测不可靠时显式指定前缀，人工核对顶层目录名）。

## B. 入口与 frontmatter（4 项）

- [ ] frontmatter 为多行 YAML：首行 `---`，逐行 `name:` / `description:` / `version:`，闭合 `---` 单独成行。
- [ ] `name` 为 kebab-case，与技能目录名一致。
- [ ] `description` 一行写完：触发词 + 输入 + 产物 + 不适用场景（长度与平台入口文案一致）。
- [ ] 正文第一段能在不读其他文件的情况下说清"什么时候用这个 Skill、产出什么"。

## C. 脚本（8 项）

- [ ] 只用 Python 3 标准库；第三方库只出现在 `try/except` 可选分支，缺了也能跑。
- [ ] 不依赖当前工作目录：`Path(__file__).resolve().parent` 推导根目录，并对多候选布局回退。
- [ ] 每个脚本 `python3 -B xxx.py --help`（或 `selftest`）退出码 0。
- [ ] 任何异常都被捕获，写入 `result.json.errors`，**退出码恒为 0**。
- [ ] 第一条写盘动作是 partial `result.json`；finalize 无条件覆盖。
- [ ] 导入期无副作用（不读文件、不起子进程、不联网）。
- [ ] 单脚本 ≤20KB、脚本总数 ≤3；没有"多阶段串行链"。
- [ ] 7–8 分钟内可跑完；约 780 秒或 56 次请求时主动 finalize。

## D. result.json 契约（7 项）

- [ ] `result.json` 可 `json.load`，16 个顶层字段齐全（缺值 `null`/`[]`/`{}`，不省略）。
- [ ] `case_id` 与输入一致（取不到才用 `unknown`，并说明来源）。
- [ ] `output_contract` 与输入逐键一致：不改名、不合并、不漏键。
- [ ] `artifacts` 里每个路径都真实存在。
- [ ] `status` 与 `coverage`/`verification` 自洽（有占位或未验证项就不能 `ok`）。
- [ ] `errors`/`degradations` 记录了所有降级，不能"降级了装作没降"。
- [ ] `runtime` 是真实请求数与耗时。

## E. 证据与质量（6 项）

- [ ] 抽 3 条 `evidence`，用原文检索能逐字命中（含 NFKC/空白/连字符归一后）。
- [ ] 每个关键数字、引用号、结论都有对应证据或明确标注"作者判断"。
- [ ] `locator` 指向真正对应的位置，没有编造页码/图表号。
- [ ] 材料缺口写在 `pending_human`，每条带可执行下一步。
- [ ] 冲突信息保留双方，没有擅自统一。
- [ ] 没有"提升 X%""显著优于"之类无对照数据的自述。

## F. 负例回归（4 项，看是否"仍然产出合法结果"）

| 负例 | 期望行为 |
|---|---|
| 空 `/input` | 输出 `status=failed` 或 `partial` 的合法 `result.json`，`errors` 说明无输入 |
| `case.json` 损坏 | 不崩溃，`case_id=unknown`，其余仍按可读材料产出 |
| 附件缺失/无文本层 | 记 `degradations`，相关字段 `unknown`，其余材料照常成稿 |
| 超长输入 | 按时截断并记录截断位置，先 finalize 再考虑扩写 |

- [ ] 四个负例都跑过，且都产出了合法的 `result.json`。

## G. rubric 维度 ↔ 检查项映射（用于红队复审）

| rubric 维度 | 自检时要能回答 |
|---|---|
| 实际效果 40（完成度/正确性/完整性/可核验） | 主产物是否真的完成任务？关键结论是否与原文一致？任务要求项是否逐项覆盖？每条结论能否回原文？ |
| 使用增益 25（质量/效率/可验证） | 相对基础 Agent 多了什么可观察的东西（覆盖率计数、校验通过率、字段化结构）？这些数字能否被复核？ |
| 创新增益 15（新能力/方法/证据） | 哪个能力是"基础 Agent 难稳定做到"的？它在哪个字段/产物里可见？ |
| 可靠体验 10（调用/稳定/异常） | 触发条件是否明确？重复运行是否一致？异常分支表是否覆盖常见坏输入？ |
| 生态贡献 10（文档/复用/推广） | 换学科/换材料要改哪里？字段字典、规则文件、最小示例是否齐备？ |

## H. 60 秒快速协议（每次提交前最低限度）

1. `ls -R submission | head -50`：看目录与文件数。
2. `python3 -c "import json,sys;json.load(open('submission/resources/result_schema.json'))"`：自己能解析的 schema 先过。
3. 逐个脚本跑 `--help`：全 0 退出。
4. 空输入跑一次 finalize：产出合法 `result.json`。
5. `grep -R "TODO\|FIXME\|__pycache__\|PLACEHOLDER" submission`：无命中。
6. 人工看一遍 SKILL.md 的"核心流程"命令：路径都是自算的，不是写死的。

## I. 提交前 3 条"千万不要"

1. 不要在没跑过负例的情况下提交（空输入即崩的包必失败）。
2. 不要为了"更完整"临时加脚本/加资源（二期实测：加功能几乎必然掉分）。
3. 不要把示例输出写成正式结果、或把示例文件放进正式输入扫描路径（会被当成材料）。
