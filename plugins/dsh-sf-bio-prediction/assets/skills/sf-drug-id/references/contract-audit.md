## 1. 文件契约检查清单（49 项，归为 12 类）

逐项用脚本检查，**任何一项不过都不提交**。本次实际运行 49 项 / 0 问题。

| # | 检查类 | 通过标准 |
|---|---|---|
| 1 | 编码 | UTF-8 可解码、**无 BOM** |
| 2 | header | 精确等于 `sample_id,predicted_drug_id`（无空格、无多余列） |
| 3 | 字段 | 每行恰好 2 个字段、无空字段、无引号异常 |
| 4 | 行数 | 行数 = 测试集行数（本次 1,370） |
| 5 | sample_id 唯一 | 1,370 个互不相同 |
| 6 | sample_id 集合 | 与测试集相等：missing = 0、extra = 0 |
| 7 | 行序 | 与测试文件原始顺序一致（兜底：即使评分器按行对齐也正确） |
| 8 | 预测合法 | 全部 `predicted_drug_id` ∈ 候选清单 |
| 9 | 一一对应 | 每个候选恰好出现一次（1,370 unique，集合相等、构成排列） |
| 10 | 无重复/多余/缺失 | 三类均为 0 |
| 11 | 体积 | 文件 ≤64 MiB（本次 39,759 B），提交包解包 ≤64 MiB（本次约 403 KB） |
| 12 | 合规 | 代码审阅确认无 sample_id / 文件名 / 外部注释回查；方法来自特征 + 匈牙利 |

建议把检查写成一次性脚本，对**每个候选**都跑（候选文件可能不同，格式相同）。

## 2. 提交包（bundle）契约

除了最终的 `predictions.csv`，评测方可能以不同方式读取产物，因此提交包要覆盖所有读取路径：

| 检查 | 要求 |
|---|---|
| 产物位置 | 包内 `outputs/predictions.csv`，并保留一份 `results/predictions.csv` 副本，两份逐字节相同 |
| 清单一致 | 提交清单的 `expected_outputs` 指向 `outputs/predictions.csv`，与实际文件哈希一致 |
| 入口脚本 | 若评测方会执行入口脚本（replay）：脚本必须能用**纯标准库**重建或校验产物（内嵌冻结预测更稳），从任意工作目录可运行；**不得删除或覆盖**已有正确产物 |
| 依赖 | `requirements.txt` 为空或零第三方依赖；容器文件无 RUN/pip/网络访问 |
| 完整性 | zip 校验通过；不含 `__pycache__`、点文件、样本混入、凭据、绝对路径 |
| 体积 | 本次正常包约 0.4 MB；远小于上限 |

回退策略：准备一个「安全版」提交包 —— 只替换入口脚本为纯标准库的产物重建/校验脚本，其余成员逐字节不变；用 4 种场景仿真（原样运行 / 删除产物后重建 / 产物写坏后修复 / 换工作目录运行），要求产物哈希全部正确。

## 3. 评测覆盖矩阵

| 评测方式 | 普通包 | 安全版包 |
|---|---|---|
| 直接读包内 `outputs/predictions.csv` | ✅ | ✅（逐字节相同） |
| replay 入口脚本后读 `expected_outputs` | ⚠️ 入口脚本若不重建产物则失败 | ✅ 纯标准库重建并校验哈希 |
| 读 `results/predictions.csv` | ✅ 副本相同 | ✅ 副本相同 |
| 入口脚本在只读目录 / 其它工作目录运行 | ⚠️ 可能不产出 | ✅ 按脚本自身位置定位包根；只读时校验已有文件 |
| 依赖 pandas/scipy | ✅ 不需要 | ✅ 纯标准库 |

## 4. 评分器故障的判据与处理（实测）

### 4.1 判据：区分「评测失败」与「0 分」

| 字段/现象 | 含义 |
|---|---|
| 状态 = evaluation_error | 评测器没有真正评分；此时显示 0 **不代表方案得 0**，不能当 0 分接受 |
| 通常不计入额度 | 失败提交不消耗额度，可安全重投（以平台字段为准） |
| 同时间窗多题同时失败 | 平台级故障；不要连续重交烧额度 |
| 队列位置长时间不前进 | 评测队列冻结；先等恢复 |
| **只有本题所有提交恒 0、其他题出真实分** | 本题专属评分器未生效（不是方案错误，也不是平台整体故障） |

### 4.2 本题的故障证据链（可直接复用的写法）

1. 本题所有已评分提交均为 0；同期其他题能拿到与题面 metric 吻合的真实分（如另一题 54.82 与本地 CV 54.56 吻合、另一题 40.0 与子题结构吻合）。
2. 本方法产物已通过 49 项契约检查（0 问题），且本地 CV macro recall 0.899/0.915，按题面预期 82–91 —— 不是格式或方法问题。
3. 平台侧该题的评分配置显示为人工复核、无自动评分器（对比：同批其他题有程序化评分器生效）。
4. **路径实验**：把 `predictions.csv` 同时写入包内 outputs/results、当前工作目录、以及题面可能的工作目录等多个位置（共 12 个候选路径），bundle 上传确认成功，结果仍为 0 → 排除「评分器找错路径」的假设。
5. 结论：该题缺少生效的自动评分器。动作：保留产物、按题面口径发起人工复核；不再消耗额度。

### 4.3 恢复后的动作（最有价值的策略）

- 保留一份「正式版」产物与提交包，等评分器修复后**用同一份产物重交**。本次：修复后重交直接得 90.58，随后迭代到 93.28。
- 恢复信号：此前失败/0 分的提交被自动重评出真实分；或新提交拿到真实分。平台曾在故障后自动重评失败批次（另一题的实例：首评失败后约 29 分钟自动重评出真实分）。
- 自动重评期间不要重复提交同内容；先观察队列。

## 5. 候选版本管理（额度是稀缺资源）

1. 每个候选目录一套完整产物 + 方法说明；记录：候选名、sha256、CV Fold A/B、线上分、与上一版差异数。
2. 提交前先跑契约审计与「两份产物 sha 相同」检查，避免用额度提交重复文件。
3. 额度分配（本次平台每题 10 次/日）：早期锚点 1 次；每档 ≥0.5pp CV 提升 1 次；**最后 2 小时保留 30%**。
4. 评分器故障期不消耗额度做重投；故障判定后把额度留着。
5. 结束前锁定「当前最高分候选」，不要用最后一发做探测/验证用途。

## 6. 反泄漏四检（提交前必跑，与格式审计同等重要）

1. **查询行置换等变**：打乱查询行序重算 CV，指标必须完全不变（本次 Fold A 0.9029→0.9029、B 0.8876→0.8876、C 0.7088→0.7088）。
2. **标签打乱对照**：随机置换 reference 药物行后 macro recall 应掉到随机水平（约 1/1370）。
3. **权重随机化对照**：随机重排 ICC 权重后性能应显著下降（本次掉到 0.65/0.57/0.45）→ 证明增益来自真实跨剂量可靠性。
4. **只用参考剂量拟合**：ICC/协方差/质心仅用参考剂量行；目标剂量只做无标签的 z-score 与减全局均值。

红线：任何依赖「查询行序 = 真值序」的后处理（对称化、按对角修复互换对等）都是行序伪影 —— CV 虚高、线上必崩，不得进入提交版本。

## 7. 可复制的最小审计命令清单（不依赖具体路径）

1. 读 `predictions.csv` → 检查 BOM/header/行数/字段数。
2. 读测试表与候选表 → 集合运算得 missing/extra/重复/清单外四个计数，全部必须为 0。
3. 断言预测列为候选集的一个排列（长度相等且集合相等）。
4. 检查体积上限与 zip 完整性；扫包内是否有点文件/缓存目录。
5. 记录文件 sha256 与 CV 分项，写入版本台账。
